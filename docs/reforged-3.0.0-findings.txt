PART 1. HOW THIS WAS OBTAINED, AND A CORRECTION
================================================================================

THE CORRECTION FIRST. Earlier in this work it was reported that pre-3.0.0 data
was unreachable and that a before-and-after diff was impossible. That was WRONG.
The cause is worth recording because it is a trap that reads exactly like a
finding.

Blizzard's CDN addresses files by ENCODING key. Requests were being made with
CONTENT keys, which return 403. Because the CURRENT build failed in exactly the
same way, the failure looked like a protocol limitation rather than an error in
the request, and a control that agrees with a mistake confirms nothing. The
control was real and the conclusion drawn from it was not.

THE WORKING CHAIN, all four hops verified.

  1. Build config. The install caches the configuration of the build it
     replaced. This machine holds 2.0.4.23745 alongside the active 3.0.0.24268.
       C:\Warcraft III\Data\config\9a\94\9a94ff7d25781db6c09190cd69d52458
       C:\Warcraft III\Data\config\3a\9d\3a9d8f26806936764d2d9ad526a65e04

  2. Encoding table. Fetched from the CDN by the encoding key in the config,
     BLTE decoded, and parsed. It maps content key to encoding key.
       2.0.4  7,665,862 bytes decoded, 119,851 content keys
       3.0.0  8,846,470 bytes decoded, 138,362 content keys
     MEASURED. Both downloads matched the byte count the build config declares
     EXACTLY, carry the BLTE magic, and every chunk md5 verifies.

  3. Root. The root content key resolves through the encoding table to an
     encoding key, which fetches a plain text file list of the form
     path|ckey|tags|installpath.
       2.0.4  16,332,038 bytes, 135,414 paths
       3.0.0  21,145,250 bytes, 174,908 paths
     MEASURED. The 174,908 figure independently agrees with the 175,026 names
     counted through CascLib against the local install, which is the kind of
     two-route agreement worth having.

  4. Content. Ordinary files are NOT served loose. They live in CDN archives
     and are reached by a ranged GET using the offset and size in an archive
     index. The install carries 213 index files in Data\indices.

A PARSING BUG WORTH RECORDING. The encoding table's espec block size is a
uint40 at byte 17, and the block starts at byte 22. Reading the field one byte
later parses 91 as 23,394, which puts the page area 53 bytes off. It did not
error. It landed on plausible looking data and returned a partial table of
5,200 keys instead of 119,851, with the root key simply absent. Found by
locating a known content key in the raw bytes and confirming its entry sits at
an exact multiple of 38 bytes from the page start.

A SECOND ONE, SAME SHAPE. The archive-group index uses a 5 byte offset into a
virtual concatenation of all archives, while a real archive index uses 4 bytes.
Feeding a group entry to the fetcher produced an offset of 601,563,851,245 and
a hash that is not a fetchable file, which answered 403. Restricting the lookup
to the 190 real archives fixed it. That 601 GB number is meaningless and is NOT
the size of anything.

MEASURED, the real CDN figures.
    archives listed in the active CDN config      190
    stored files across them                      284,300
    stored, compressed content                    46.6 GB
    size cap per archive                          exactly 256.0 MB
    local install Data\data                       32.8 GB across 59 files

PART 8. MEASUREMENT ERRORS MADE AND CORRECTED
================================================================================

Recorded because each produced a confident wrong answer that read like a
finding, and the corrections are worth more than the original claims were.

 1. REPORTED PRE-3.0.0 DATA AS UNRECOVERABLE. Wrong. Requests used content
    keys where the CDN wants encoding keys. The current build failed
    identically, so the error looked like a protocol limit. A control that
    agrees with your mistake confirms nothing.

 2. REPORTED 74 REMOVED LINES FROM TriggerData.txt. Wrong. Those were edits,
    which a line diff scores as delete plus insert. A key-set comparison gives
    zero removals. This nearly became "3.0.0 removed 64 GUI functions".

 3. ENCODING PARSER READ espec_size AT THE WRONG OFFSET. Returned 5,200 keys
    instead of 119,851 with no error, and the root key simply absent.

 4. ARCHIVE LOOKUP INCLUDED THE ARCHIVE-GROUP INDEX. Produced a 601 GB offset
    and a 403. That number is not the size of anything.

 5. WRONGLY FLAGGED CATASTROPHIC DATA LOSS. 105.3 MB to 71.9 MB after repair
    was recompression. Uncompressed content GREW by 1.15 MB.

 6. MPQ FIX ATTEMPT TWO FILTERED ON hash.IsAvailable, which excludes exactly
    the odd locale slot, so nothing changed.

 7. A VACUOUS TEST. A hermetic duplicate-entry test passed on broken code,
    because a reflection-seeded twin does not survive SaveToBytes.

 8. NATIVE PROBE, TWO ERRORS. A line-anchored regex reported a 4.5 MB script
    defined 0 functions, because obfuscators strip newlines. Then two-pass
    comment-and-string stripping ate the closing quote of any literal holding
    a double slash, swallowed 67% of the script, and reported 54 real function
    definitions as missing natives. The tell was 67% against 11% on a
    comparable map.

 9. IMPORTS FIX INCOMPLETE. Filtering only the archive side turned 13 rows
    from wrong-kind into wrong-and-missing.

10. COLLECTOR SCRIPT assumed drive letters and crashed on an unmounted D.


================================================================================
PART 9. PERFORMANCE, AND HOW TO RUN IT FAST
================================================================================

MEASURED, the whole progression on the same work.

    first version      timed out at 540s having finished 4 of 24 files
    plus cache and cell diff     60.0s for all 75 core behaviour files
    fully structural             4.33s for all 75

Three causes, and only one of them was the network.

 1. difflib.SequenceMatcher was the whole problem, and it was ALSO WRONG. It
    scores an edited value as a delete plus an insert, so on UI/TriggerData.txt
    it reported 74 removed lines where the true answer is zero. On
    Units/UnitSkin.txt it took 21.8 seconds by itself, which was 60% of the
    entire run.

    Every file in this build has structure, so use it. A key set comparison is
    one hashing pass and it answers the question actually being asked, which is
    what was added, removed or changed. It is both linear and more correct.

        .slk                  cell diff keyed by object id and field name
        .txt .fdf .ini        section and key diff
        .j .lua .ai           function level diff, body hashed
        anything else         line multiset

 2. Every run re-read 40 MB of archive indices and re-decoded two multi-megabyte
    encoding tables to rebuild maps that cannot change for a fixed build. Built
    once and cached now, 49.3 MB.
